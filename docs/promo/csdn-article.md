## 正文

先说结论：这是一个**用 Java 17 + Spring Boot 3.4 + Spring AI 写的长篇小说生成流水线**，Apache-2.0 开源。

项目地址：https://github.com/YonRen-code/Novel-factory

它解决的不是"能不能生成"，而是长篇连载最要命的那个问题——**写到几十章以后，AI 开始自相矛盾、忘掉伏笔、时间线乱套**。

### 一、开始之前：你最少需要准备什么

这一点我放在最前面，因为它决定了你会不会被劝退。

**必需：只有一个 OpenAI 兼容端点的 API Key。** DashScope（百炼）、DeepSeek、Kimi 都测过，任意一个都行。

**可选：一个 embedding 模型 + 一个 Qdrant（Docker 一行命令）。** 加上它才会开启向量增强——跨章记忆的语义唤醒、动态参考资料检索。

**不加也能跑通全流程。** 三账本、章节摘要、伏笔排期、一致性索引、批末体检这些文件侧记忆功能一个都不少，只是检索方式退化。而且系统不会静默降级——批末体检里有一项「无检索唤醒章数占比」会明确告诉你哪几章是裸跑的。

```bash
# Qdrant 可选，想开就一行
docker run -d --name qdrant -p 6333:6333 -p 6334:6334 qdrant/qdrant
```

为什么强调这个？因为市面上很多"长篇小说生成"项目一上来就要求你配向量库、配数据库、配一堆东西，实际上大部分机制根本不依赖它们。**门槛应该由效果决定，而不是由架构图决定。**

### 二、AI 写长篇小说的 7 个真问题，和我的解法

这一节是全文最核心的部分。每一条都是我在实际跑到 65 章、1 亿 token 之后才真正明白的。

**1. 失忆：设定漂移、自相矛盾**

模型不记得第 8 章埋了什么。把前文全塞进上下文是没用的——迟早要截断，而且是静默截断。

解法是**三本账本外置**：角色、物品、势力各一本，每章新出现的事实强制入账，下一章动笔前把账本当前状态装配进前缀。账本不是让模型自己记，而是落成可 diff 的 JSON 文件。

关键在"强制入账"怎么保证——模型会编造正文里没有的事实。所以每条状态都必须附一段**正文原文引证**（≤50 字），再用机械匹配验证这段引证真的存在，匹配不上就不入账。这一层不做语义判断，纯字符串比对，放宽的是表述，不是事实的有无。

**2. 时间线混乱**

很多生成器的正文时间靠模型自己推，写着写着主角年龄就对不上了。

解法是**时间推进只走计划显式声明的额度**：每章计划必须声明 `timeAdvance`，这是唯一合法的推进通道，正文写完再机械核对一次。蓝图层再加年份/年龄的合法区间校验。

**3. 伏笔挖坑不填，或者埋了立刻收**

解法是**排期状态机**：每个伏笔有"计划埋设章 / 计划兑现章 / 状态"，状态流转 `PLANNED → PLANTED → PAID`，卷末强制清账。逾期未埋的标 `MISSED`，清账时还要裁决"是真兑现还是静默兑现"。

积压到一定量会触发**动态权重**：滞留章数 ×5 + 重要性 ×10，超过阈值就必须逐条评估。但主线核心永不冻结——这是踩过坑才改的，早期版本把第 11 章的主线谜题给冻结了，结果写手失去了主线悬念的上下文。

**4. 叙事退化**

三种典型形态：对白坍缩（连续几章全是对话）、原地循环情绪注水、主线卡在同一个悬念档位不动。

解法是**机械门禁**：段落结构策略、对白比例策略、内容密度策略、悬念阶梯策略（检测档位倒退和连续 3 章同档）、疲劳词表（内置 60+ 中文套话词，可外部覆盖）、已用情节黑名单（舞台复用次数、同类冲突方连用、能力展示章数）。

这些都不靠模型自评，全是可复算的统计量。

**5. 上下文预算冲突**

前缀由 8 个以上的块拼成——末态红线、记忆、风格警示、一致性索引、禁泄清单、情节黑名单……每块单独有封顶，但**封顶之和会击穿模型输入窗口**。

解法是**块优先级淘汰**，而且关键设计是**渲染顺序与淘汰次序分离**：超预算只影响谁被丢，不影响谁排在前面。其中"禁泄清单"标记为不可截断——它靠逐字扫描同源，截断会静默丢词，所以放不下就整块丢弃**并在日志里点名**。

**6. 结构化输出不合规**

模型返回的 JSON 偶尔会缺引号、多逗号、带未转义换行。

解法是每个结构化调用都有兜底路径：JSON 修复 → 按字段抢救 → 换模型重试，最后才降级。解析失败不会中断整批。

**7. 供应商不稳定**

500、超时、欠费、模型下线，报错五花八门。

解法分三层：**错误分类**（7 类，每类带两个正交判断——"同模型重试有没有意义"和"换模型有没有意义"，比如上游 engine abort 属于换模型有效、原样重试无效）、**跨模型族降级链**（备选尽量跨族，因为免费额度和上游拒绝常按模型计量，同族备选可能一起挂）、**token 预算熔断**（按作业累计，命中后当前章写完即停，不留半截）。

### 三、工程设计

**四层规划**：卷蓝图 → 阶段蓝图 → 段计划 → 章计划。每批写完的摘要、新入账事实、新埋伏笔作为"既定事实"回灌下一批。

**写手动笔前的输入装配**：本章计划、前情摘要、三本账当前状态、一致性索引、向量检索召回的相似情节、在途伏笔视图——总预算约 1.8 万字符，超了按块优先级裁。

**质量管线**：段落密度审校 → 审校门（BLOCKING 级必修）→ 修订 → 低置信章触发"候选挑战者"盲写盲评。**挑战者刻意用另一个模型族来写和评**，专门对抗"自己评自己"的自偏好；复审不过就自动退回原稿，保证拒绝率不上升。

**代码规模**：主代码 3.0 万行，测试 2.3 万行，106 个测试类、1114 个用例。另有 6 个类、1428 行的离线校准评测框架（审校校准、跨系统盲评），需要显式开关才运行。

### 四、批末体检：把"这批比上批是好是坏"变成可归因的

这是这个项目我最满意的部分。每批结束后出一份**26 项量化指标**的报告，每项三列：当前值 ｜ 目标（带历史基线）｜ 明细，分四档 OK / WATCH / DEGRADED / CRITICAL，每条劣化指标后面跟可执行建议。

真实输出节选：

```text
OK       账本完整度       94.06%（目标 ≥90%） ｜ 严格 523 / 放宽 47 / 挂起 11
OK       对白轮次密度     22.50次/千字（目标 ≥9）
WATCH    候选选优触发率    52%（目标 ≤30%） ｜ 触发 39 / 65 章
DEGRADED 进度对齐        7段（目标 ≤1 段） ｜ 第 65 章按大纲应处【61-70章 2009年/11岁】段
建议：进度滞后约 6 年：……两条出路：①规划层加速（跳月/压缩日常）；
②承认慢节奏，重排大纲章段预算。不应长期维持现状——路标与正文漂移会越滚越大。
```

**每条 DEGRADED 都对应一个可执行的下一步。** 这是它和"生成完就结束"的工具最大的区别——你能定位到是哪一层机制没生效，而不是只能靠感觉调参。

### 五、它真的跑过：1 亿 token 的实测数据

不是 demo。工作台里有一张运行观测卡片，直接读 `llm-usage.jsonl`：

- 调用次数 **7,686 次**
- 累计 tokens **1.03 亿**（输入 8564.8 万 / 输出 1701.9 万）
- 累计耗时 **76.3 小时**
- 失败率 **1.86%**
- 平均单次调用 **35.7 秒**

【配图 3：运行观测卡片 —— 上传 `docs/images/workbench-observability.jpeg`】

**1.86% 的失败率是这套降级设计的直接产物。** 单模型裸跑的真实失败率远高于此，差额由错误分类 + 跨族降级链 + 分层重试吃掉了。

输入占 83% 也说明一件事：分层记忆前缀的设计是有代价的——每章正文都带着完整前缀。所以优化成本的第一顺位不是换便宜的输出模型，而是看前缀预算日志，定位哪一块膨胀了。

### 六、快速开始

```bash
git clone https://github.com/YonRen-code/Novel-factory.git
cd Novel-factory

# 1) 配 Key（唯一必改项）
export LLM_API_KEY=sk-你的密钥
#  或复制 config/application-local.example.yml 到
#  novel_factory-app/src/main/resources/application-local.yml 后填入

# 2) 打包（约 20 秒，不需要预先安装任何模块）
mvn -pl novel_factory-app -am clean package -DskipTests

# 3) 启动（注意 package 只打包，不启动服务）
java -jar novel_factory-app/target/novel_factory-app.jar
```

然后浏览器打开 **http://localhost:8080** —— 前端随 jar 由后端同源提供，不需要另起静态服务器，也不需要打开本地文件。

【配图 4：场景模型矩阵 —— 上传 `docs/images/settings-model-matrix.jpeg`】

设置页可以完全用表单配置：全局接入、embedding 独立分区（不同供应商、不同密钥、不同维度）、以及 16 个生成场景的模型矩阵。每个场景可以独立指定模型、温度、思考开关，甚至独立的 base-url 和 api-key——**这样评审场景就能指向另一个模型族，保证盲评中立**。改动保存即生效，落到运行时覆盖文件。

### 七、成本，以及它做不到什么

**成本**：每章 8~25 万 token（视质量档位），一批 5 章大约 80 万。这是"全链路审校 + 候选重写"的定价。预算敏感就把候选触发关掉，那是最贵也最可省的一环。

**学生党**：阿里云百炼有 300 元额度可领，`qwen3.8-flash`、`deepseek-v4.1-flash`、`deepseek-v4-pro`、`glm-5.2` 以及嵌入模型部分可以免费调用，够把整个流程跑完几批。

**做不到的**：
- 面向中文长篇设计，分词、账本、体裁模板都以中文为前提
- 单机文件存储，多机协作/多人共写不在范围内
- 做不到完全无需人工审核，所以没设计"一次跑多本"的架构
- 大纲需要按"章段 + 时间标记"格式自己写
